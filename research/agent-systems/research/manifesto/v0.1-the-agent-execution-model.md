# The Agent Execution Model

> **Version 0.1** · Proposal · July 22, 2026  
> This proposes Agent Systems Engineering as a coherent discipline. It is not definitive. It is a framework intended to be tested, challenged, and refined.

---

## Chapter 1: The Missing Discipline

Every discussion about AI agents converges on the same limited dimensions. Which model is best? What prompts work? Which framework should we use? These are surface questions hiding a structural problem: the field has no shared architectural vocabulary.

Software engineering solved this in the 1960s by moving from "elegant functions" to layered architectures, separation of concerns, interface contracts, and design patterns. Not because individual programmers got better — because the industry recognized that complexity demands structure, not cleverness.

We are in the same moment with agents. Every production agent system that scales reveals the same gaps — every team independently rediscovering what another team already learned elsewhere, at greater cost. Because there is no shared architecture, only shared intuition.

Experienced engineers building browser automation systems and desktop automation systems arrive at the same structural decisions — hybrid perception, confidence scoring, budget-aware routing — but under different names, without sharing insights. The gap between them is not knowledge. It is vocabulary and structure.

Agent Systems Engineering proposes the structure. Not to constrain creativity. To channel it into patterns that survive tool changes, model shifts, and architecture evolution.

The gap is not the absence of expertise. The field is filled with talented engineers. The gap is the absence of a unifying framework that connects software architecture, ML operations, and computer science theory into something actionable — an architecture that tells you exactly where each piece belongs, what it guarantees, and what it explicitly does not.

Current agent architecture looks like this:

```
[Model] → [Some Logic] → [Action] → [Observe Result] → Loop?
                ↓ (sometimes)
           [Memory?] Maybe.
```

A workflow diagram dressed up as an architecture. No defined interfaces. No explicit contracts. No separation between what's timeless and what's implementation-dependent. No governance layer. No observability model. No economic accounting.

When these systems break at scale, the debugging process reveals that nobody thought about where the boundary between perception and decision-making should live, or whether recovery strategies should be embedded in execution or handled separately, or why verification needs to see what perception saw.

A mature discipline provides properties that an ad-hoc approach cannot: knowledge compounds instead of evaporates. Interfaces are explicit instead of inferred. Architecture survives tools. Errors become pattern-recoverable instead of mysterious. Economics becomes measurable instead of discovered too late.

That last point is critical. Economics is not an optimization layer on top of agent architecture. It is a structural concern baked into every layer — from perception modality selection to model routing to retry budgets. When economics becomes a first-class architectural concern rather than an operational surprise, agent systems become viable at scale.

## Chapter 2: The Agent Execution Model

Everything about agent systems converges on a single structure. Not twenty-four nodes. Not a complex flowchart. A loop:

```
      Perception → Decision → Planning → Scheduling
            ↑                             │
            │        Execution ← Verification
            └──── Recovery ← Learning ←───┘
```

Perception converts environmental signals into structured observations with confidence scores. Decision Engine transforms observations into intents. Planning decomposes intents into actionable steps with dependencies. Scheduling orders steps temporally and allocates resources. Execution carries out scheduled actions on execution surfaces. Verification checks whether execution achieved its intended outcome. Recovery handles detected failures through root cause diagnosis and retry strategies. Learning improves future performance based on past experience.

These eight nodes are not optional components you add or remove based on your use case. They are structural requirements that emerge from the fundamental challenge of building autonomous systems interacting with uncertain environments. You can collapse some — Planning and Scheduling might live in one module — but you cannot eliminate any without breaking the system at scale.

This is not a ReAct pattern. It is an architecture. ReAct gives you Perception → Decision → Action. Your loop has eight nodes. The ReAct practitioner discovers after months of production debugging that they needed verification, recovery, and learning — not extensions of ReAct, but structural necessities that emerge when systems scale beyond proof-of-concept.

More importantly, the Agent Execution Model provides **interfaces** between nodes. When Verification detects a task failure, it doesn't guess what kind of failure occurred. It knows the contract: Execution produces observable outputs, Verification compares expected against actual, Recovery receives classified failures. This is what makes it an architecture and not a pattern. Patterns tell you what to do. Architectures tell you what to depend on, what to guarantee, and what to explicitly not guarantee.

### The Six Layers

Around this core loop, six architectural layers emerge organically. They are not add-ons. They are structural consequences of the loop itself. Remove any one and the system breaks at scale.

**Memory** exists because agents operate in bounded context windows but face unbounded problems. Working Memory (current context), Long-term Memory (retrievable patterns), and Environment State (external reality independent of perception) form the memory triad. Without structured memory, every step starts from zero. With it, agents compound knowledge across sessions.

**Economics** exists because every operation has a cost — tokens, latency, compute. Perception modality selection is a cost decision. Model routing is a cost decision. Caching strategy is a cost decision. When economics is woven into every layer rather than tracked separately, agent systems become economically viable.

**Observability** exists because non-deterministic systems must be traceable. Spans (individual operations) chain into traces (causal sequences). Without it, failures are black boxes. With it, every failure decomposes into its component decisions — the observation that triggered it, the model that evaluated it, the action it produced.

**Security** exists because agents that can perceive and act autonomously are privileged access points by definition. Context isolation, instruction quarantine, action approval gates, same-origin boundaries — these are architectural necessities, not compliance checkboxes. Traditional security protects systems from external attackers. Agent security must also protect external systems from internal failures — a buggy agent is functionally equivalent to an attacker with legitimate credentials.

**Governance** exists because autonomous decisions at scale create accountability problems. Policy enforcement, audit trails, compliance checking, consistency controls ensure that probabilistic agents remain traceable, auditable, and compliant. Autonomy without accountability is recklessness.

**Runtime** exists because logic needs a host. Containers, servers, edge devices — the runtime determines what's possible at the physical level. No architectural elegance compensates for a runtime that cannot support the required throughput, latency, or surface access.

Six layers. Eight loop nodes. One mental model. Everything in agent systems engineering maps to this structure.

## Chapter 3: Execution Surfaces

The same architecture operates across different environments. What changes is the **execution surface** — the medium through which perception acquires signals and execution produces mutations. The architecture remains constant.

### The Browser Surface

Browsers offer the richest signal ecosystem: accessible DOM trees, screenshots, console logs, network traffic, cookies, storage APIs. Three perception architectures coexist in production.

AXTree-primary reads semantic UI metadata at 200-400 tokens per snapshot. Fast, reliable on well-built sites. Fails on custom widgets and canvas elements.

Vision-first captures screenshots and describes them. Universal coverage. Expensive and slow.

Hybrid combines both — AXTree as primary, vision as fallback when confidence drops. Production default for serious systems. Best balance of cost, reliability, and speed.

Economies matter especially for browsers because token costs accumulate fast. Caching provides 70%+ hit rates. Model routing saves 85%+ on budget tasks. The browser surface is where agent systems engineering proves itself — it is simultaneously the most data-rich and the most hostile environment an agent can encounter.

### The Other Surfaces

**Desktop environments** trade structure for ubiquity. Every application has its own UI paradigm, and most provide only pixels — accessibility APIs exist but coverage is spotty and inconsistent.

**Terminal environments** offer the purest input/output model with structured stdout/stderr, but command output formats vary wildly and error handling follows no standard.

**API surfaces** are the cleanest match for the Agent Execution Model by design — typed request/response protocols, explicit schemas, versioned contracts. They're also the most constrained by definition: agents can only automate what APIs expose.

**Mobile interfaces** blend WebView components with native controls, each app presenting a unique interaction model that requires surface-specific tooling.

**IoT systems** close the loop on the physical world — real-time sensor streams, actuators, strict latency budgets — but face environmental constraints that digital surfaces don't: power limits, network unreliability, hardware wear.

Each surface offers different signals and mutation capabilities. But the architecture treats them uniformly: Perception always converts signals to observations with confidence scores. Decision always transforms observations into intents. And so on. This uniformity lets knowledge transfer across domains — a pattern discovered optimizing browser perception modality selection informs how IoT systems choose between camera and lidar feeds.

Without this abstraction, every surface gets treated as a separate problem domain. With it, the entire field benefits from insights discovered on any single surface.

## Chapter 4: Why This Matters

The field is moving through three phases, and we're at the boundary between two.

Phase 1 was Automation (2020-2023): deterministic scripts with LLM assistance, brittle selectors, failure on layout change. Enhanced automations wearing agent clothes.

Phase 2 is Agents (2024-2025): perception, reasoning, action on unknown environments. Impressive demos. Unpredictable production. Exploding token costs. Every team rebuilding the same structural decisions from scratch. Security audits exposing vulnerabilities that had nothing to do with models and everything to do with missing architectural layers.

Phase 3 is Systems Engineering (2026+): the question stops being "can the agent do the task?" and becomes "can the system do it reliably, economically, securely, and at scale?" Teams building serious systems are already converging on these solutions — hybrid perception, classified recovery, model-aware budget routing, systematic observability — without knowing that other teams have already arrived at the same conclusions through different paths. Agent Systems Engineering codifies what practitioners have been learning the hard way, so the next wave doesn't have to.

If the field doesn't develop a formal discipline, it stays stuck in Phase 2 indefinitely. Every new agent project becomes a one-off exercise in rediscovering what others already figured out. The economic waste alone is significant: every team independently learns that caching perception observations cuts costs by 70%. Every team separately reinvents confidence scoring and model routing heuristics. None benefit from the others' discoveries because there is no shared framework for knowledge transfer.

The security implications are more severe. Without governance and security layers built into the architecture, agents operate as unrestricted automation — reading sensitive data, modifying systems, executing commands — with no policy enforcement, no audit trails, no accountability. As agents gain broader access, this gap becomes a liability, not a feature.

What a discipline provides that Phase 2 cannot:

A **shared vocabulary**. "AXTree primary with vision fallback" describes a specific pattern instead of having ten different names depending on who uses them. Knowledge transfers cleanly between teams.

**Explicit contracts**. The interface between Perception and Decision Engine is specified, not implied in a Slack thread. Both sides know what they receive and what they guarantee.

**Compounding knowledge**. Patterns discovered on one surface inform optimizations on another. Architecture survives tools — normative knowledge endures while descriptive knowledge evolves.

**Engineering credibility**. A discipline with defined layers, explicit interfaces, measurable economics, and systematic governance earns the same respect that software architecture and ML Ops earned through decades of formalization. Agent systems aren't experimental hacks. They're engineered systems.

## The One Question

Why should an experienced engineer care about Agent Systems Engineering as a proposed discipline?

Because the alternative is staying stuck where every agent project is a snowflake, every production deployment reveals architectural gaps that another team already filled, every cost overrun comes from economics being an afterthought, every security incident exposes that governance was never part of the design.

Or because you could join the group building the structural foundation that turns agent development from impressive individual achievements into a compounding discipline where knowledge transfers across teams, architectures survive tool changes, and the entire field gets better with every system built.

The architecture exists. It's been stress-tested. The evidence is there. The only remaining question is whether the field treats agent systems as a collection of techniques or as an engineering discipline worthy of structure.
