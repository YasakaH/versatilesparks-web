## Why Understanding the Browser Lifecycle Matters

This chapter covers four recipes that look simple:

1. Launch and close
2. Open tabs
3. Reuse a profile
4. Configure startup

They are the simplest recipes in the book. They are also the most dangerous. A developer who skips understanding the browser lifecycle spends days debugging symptoms that are actually lifecycle misunderstandings:

- "Timeout connecting to browser" — Chrome is a child process, not a library import
- "Profile locked" — two workers cannot share the same directory
- "Cannot find my saved session" — you launched without the profile
- "Memory grew until the server died" — Chrome was never closed

nodriver 0.50.x launches Chrome as a subprocess and communicates via the Chrome DevTools Protocol over a WebSocket connection. This is a fundamentally different architecture than importing a Python library and calling functions. Everything you do in automation depends on this process being alive, reachable, and properly configured.

---

## Mental Model — The Browser Is a Separate Machine

Think of nodriver not as "a browser library" but as a **remote control for a separate machine**.

```text
Your Python Script
        │
        │  asyncio event loop
        │
        ▼
   nodriver 0.50.x
        │
        │  WebSocket (CDP)
        │
        ▼
   Chrome Process
        │
        ├── Tab 1 (independent)
        ├── Tab 2 (independent)
        └── Profile (state container)
```

The Python process and the Chrome process are independent. One can crash without the other knowing. Chrome can be killed by OOM killer while Python waits for a response. The WebSocket can disconnect even though both processes are alive.

This mental model explains every common failure in Chapter 1:
- You need `asyncio` because CDP is asynchronous — each request waits for a response over the WebSocket
- You need `close_browser()` because Chrome does not auto-exit when Python finishes
- You need `user_data_dir` because Chrome keeps state on disk, not in Python memory
- You need startup arguments because Chrome's defaults assume a human user

## Production Story

A developer built a nightly report automation. It worked locally for three weeks. He deployed it to a VPS. Every morning, the report was missing.

He spent a week debugging:
- Added retries — no change
- Added longer waits — no change
- Switched selectors — no change

On day five, he checked the server's process list. There were 18 Chrome processes running. Every nightly run had launched a new Chrome, but the close call had failed silently somewhere in the error handling. The VPS ran out of memory. Chrome couldn't start. The automation reported "browser not found" — but the developer only checked the script logs, not the system.

He added a `try/finally` block. Every single run now ensures `close_browser()` executes, even if the script crashes.

**Lesson:** The browser lifecycle is not a setup detail. It is a failure mode that repeats until you treat launch and close as a transaction that must always complete.

## Engineering Notes

### Engineering Note: async is not optional

> nodriver communicates with Chrome over a WebSocket. Every call sends a CDP message and waits for a response. This is inherently asynchronous — if you call it synchronously, your script blocks for every single command. Use `asyncio.run(main())` everywhere. There is no synchronous fallback.

### Engineering Note: close_browser() is not optional

> When Python exits, Chrome keeps running. It is a separate OS process. If you forget `close_browser()`, Chrome accumulates in your process table. After a few hours of testing, you'll have a dozen Chrome processes consuming memory. Always wrap your automation in `try/finally` or `async with` to ensure cleanup.

## Common Mistakes

### ❌ Forgetting to close the browser

Chrome stays running after your Python script exits. After a few test runs, memory fills up. The next launch fails silently.

**Fix:** Always use `try/finally` or wrap the launch in a context manager that guarantees cleanup.

### ❌ Confusing user_data_dir with profile path

`user_data_dir` is the **parent directory** containing profiles. If you pass `/profiles/worker-1` as `user_data_dir`, Chrome creates `/profiles/worker-1/Default/`. If you pass `/profiles/worker-1/Default` instead, Chrome creates `/profiles/worker-1/Default/Default/`. The next run looks in the wrong directory.

**Fix:** `user_data_dir` should point to a directory that Chrome will fill, not to an existing profile directory.

### ❌ Launching headless-only, then wondering why something needs a GUI

Headless Chrome does not support every feature. PDF printing, extensions, some media APIs, and certain clipboard operations require a visible window. If your automation needs these, do not force `--headless`.

### ❌ Sharing one profile across multiple runs

Two concurrent browsers writing to the same profile directory will corrupt each other's state. Running tests in parallel? Each needs its own profile path.

**Fix:** Generate unique profile paths per run, or use separate named profiles for separate automation tasks.

## Production Checklist

- [ ] `close_browser()` is called in a `finally` block or context manager
- [ ] Profile directory is **not** shared across concurrent workers
- [ ] `user_data_dir` points to a parent directory, not an existing Default/ folder
- [ ] Headless mode is verified for the specific website features needed
- [ ] Startup arguments are centralized in config, not duplicated across scripts
- [ ] `asyncio.run(main())` wraps the entry point (no synchronous calls)
- [ ] A simple launch → navigate → close test passes before adding complexity

## Chapter Summary

Launching a browser with nodriver is not calling an API — it is starting a separate OS process and controlling it over a WebSocket. Every failure in this chapter traces back to forgetting that distinction. Close what you open, isolate what you share, and configure what you depend on. The browser is not a library. Treat it like the separate machine it is.
